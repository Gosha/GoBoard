# Technical design draft

This document retains design rationale and implementation history, including earlier POC behavior. Current contributor rules are in [AGENTS.md](../AGENTS.md); current production layout support is described in [automatic-keyboard-layouts.md](automatic-keyboard-layouts.md).

## Implementation boundaries

These boundaries are implemented in `GoBoard.slnx`; see [AGENTS.md](../AGENTS.md#project-boundaries) for project ownership and [build commands](../AGENTS.md#build-and-validation). The POC remains intact as a runtime reference.

Use C#/.NET, SkiaSharp, and OpenVR. SkiaSharp was selected during implementation discussion. Keep keyboard behavior independent of the renderer and OpenVR so layout and input behavior can be checked without a headset.

1. **Keyboard model:** key geometry, physical key identity, labels, and pressed/latched/locked state.
2. **Windows layout service:** tracks the foreground application's input layout and translates physical keys into displayed legends.
3. **Windows input service:** emits balanced key-down and key-up events, tracks keys owned by GoBoard, and reports injection failures.
4. **Pointer interaction:** maps each pointer to its captured key and handles press, release, repeat, and cancellation.
5. **Presentation:** SkiaSharp draws the keyboard onto an `SKCanvas`. Shared key geometry supplies both drawing bounds and hit testing in a single coordinate system.
6. **OpenVR host:** owns initialization, overlay handles, texture submission, input events, visibility, and shutdown.

Use OpenVR's overlay application type with Valve's C# binding and matching native library. Pin the chosen dependency version and preserve its license. The supplied Unity tutorial remains useful for OpenVR lifecycle, events, placement, and texture submission; its Unity-specific rendering and UI code will not be used.

## SkiaSharp rendering and texture bridge

The keyboard renderer accepts the current layout, visual interaction state, and an `SKCanvas`. It does not create a window, own the OpenVR runtime, or inject Windows input. Keep the surface lifetime and submission path in the host.

The user selected an in-VR proof of concept before a desktop preview. The current POC renders a 2532x1026 SkiaSharp keyboard through persistent OpenGL textures and SetOverlayTexture, uploading only when hover, pressed keys, modifier legends, or status change. It redraws the expanded 844x342 logical design at 3x resolution, keeping logical input coordinates independent of texture pixels. The physical size is 89.77 x 36.38 cm (about 2.82 pixels/mm), replacing the visibly soft 512x256 texture. Each upload is about 9.91 MiB. Sustained interactive redraw performance remains to be measured; repeated mouse moves within a key do not redraw. The original HMD-relative panel was confirmed visible by the user. The current revision creates an independent overlay with `CreateOverlay` and `VisibleInDashboard`. It appears alongside the dashboard instead of occupying a dashboard tab. A future settings tab will be separate. Explicit mouse scale and intersection masks restrict input to the visible image, and both overlays enable SteamVR's built-in backside by clearing `NoBackside`. The installed runtime's backside color reads `#27272CB3` (dark gray, about 70% opacity); GoBoard does not modify global SteamVR settings. The user accepted the backside appearance. The current keyboard milestone contains 79 US or 80 Swedish keys, including F1–F12, navigation/arrows, Escape/Tab, Ctrl/Alt/AltGr/Shift modifiers, and an arm-then-tap Win key. KeyboardLayout supplies the same rectangles to drawing and hit testing; OpenVR bottom-left mouse coordinates are converted to the renderer's top-left logical space.

The user selected a custom grab line after the public native-control flags failed to produce a handle on the independent overlay. A separate 540x180 SkiaSharp texture uses a 180x60 logical canvas. Its center is calculated from the panel half-height plus 3.75 cm, currently about 0.188 m below the panel center, so it stays below the panel as its physical size changes. Its visible line is 10 cm x 4 mm, inside an 18 x 6 cm target. Only the line brightens/slightly enlarges on hover and turns mint while grabbed. The front background remains transparent in every state. The padded target retains a 7.5 mm gap below the panel input bounds. Its pixels upload only when that state changes. See [the native-control investigation](native-controls-investigation.md) for the earlier findings.

### Dashboard-relative positioning

The current public OpenVR interface has no overlay-parent transform setter. The POC resolves SteamVR's menu bar with `FindOverlay("valve.steam.gamepadui.bar")` and reads its bottom-center pose with `GetOverlayMouseScale` and `GetTransformForOverlayCoordinates` in standing space. This internal overlay key is a compatibility dependency, also used by [Desktop+](https://github.com/elvissteinjr/DesktopPlus/blob/master/src/Shared/OverlayDragger.cpp); it is not a promised OpenVR contract. Missing/invalid anchors hide the panel and produce a diagnostic, rather than falling back to a dashboard tab.

GoBoard stores a local pose relative to that bar. Dashboard translation/rotation updates GoBoard and its handle together; the dashboard transform is never modified. Dashboard scale is removed so it does not resize GoBoard. Initial placement is 0.30 m below the bar with a small depth offset; placement is session-only. Visible event processing and dashboard following synchronize with `WaitFrameSync` (20 ms timeout); hidden lifecycle checks run at 10 Hz.

SteamVR overlay pointer-down on the line captures the active controller and the panel-to-controller transform. While held, `SetOverlayTransformTrackedDeviceRelative` attaches both the panel and handle directly to that controller using the captured offset. This avoids the old 11 ms loop copying unpredicted controller poses into absolute overlay transforms, which the user reported as lag. There is no application smoothing; it may be a future opt-in feature. The dashboard-relative offset is maintained using display-predicted controller snapshots for release/cancellation, while SteamVR drives the held rendering. Detaching explicitly restores absolute transforms even when the position did not otherwise change. Pointer-up releases the grab. Controller tracking loss or hiding the dashboard cancels it. Legacy trigger polling provides an additional release fallback when available. Losing the owning pointer focus cancels the grab; focus changes from the other hand do not. Another pointer cannot steal the active grab. Runtime transform readbacks are not interpreted as movement, avoiding the earlier delayed-readback drift. The complete event queue is processed before a new controller attachment is committed. GrabInput requires a focused pointer, matching event/focus controller identity, finite in-bounds coordinates, and a press no more than 200 ms old that is newer than the last release and focus entry. A queued release or focus leave cancels a pending down before it moves the panel. GetPrimaryDashboardDevice is never used to guess an unidentified source. Fresh controller-identified motion delivered to the visible handle may recover focus within bounds and after the latest release/leave watermark. Recovery cannot start a grab. Older motion and queued pre-release downs remain rejected. The overlay-wide IsHoverTargetOverlay query is no longer used as a per-controller veto: it cannot identify which hand changed targets. Controller-specific leave/up events still invalidate queued grabs before attachment. Replay tests cover these sequences; edge-event logs include source, event age, and rejection reasons. Normal guarded grab/release cycles are observed locally. After headset retesting, the user could not reproduce the intermittent unintended grab and considers it fixed for now. Keep the replay regression checks and edge-event logging.

The earlier asynchronous raw-image upload path blinked during interaction. The current bridge keeps two OpenGL RGBA8 textures alive per overlay. OpenTK creates a hidden, unfocused context; Skia draws CPU pixels, the back texture receives the upload, GL.Finish completes it, and SetOverlayTexture publishes it. No image clearing or texture reallocation occurs between updates. Texture IDs remain alive through overlay destruction and OpenVR shutdown. Skia CPU pixels have top-first rows, so both overlays explicitly use texture bounds U 0→1 and V 1→0 for OpenGL presentation. This corrects the vertical reflection reported after switching from raw images; overlay poses and mouse geometry stay unchanged. Runtime readback confirms these bounds, and rays through q, Start, Shift, and Right still return their original logical coordinates. Visual confirmation of the correction is pending. Rendering Skia directly onto GPU surfaces remains a possible later optimization.
The raw-pixel path has passed a local SteamVR smoke test at 1536x768, with full texture dimensions confirmed through runtime readback; the handle texture is 540x180. Automated pose checks cover retained offsets across dashboard translation/rotation, capture without snapping, controller rotation, and following after release. Live ray-intersection checks hit inside and miss outside the 0.45 x 0.225 m image. The user previously confirmed improved input bounds/following. Custom handle ray checks pass across its padded target and miss beyond it. Controller attachment/detachment and frame synchronization pass a hidden-overlay runtime check. The user accepted the revised direct controller movement and padded target. The user confirmed the previous 2048x1024 texture was very sharp and requested a middle ground. The earlier 1536x768 trial retained physical size and uses 44% fewer pixels; headset comparison is pending. The persistent OpenGL bridge passes a runtime smoke test and 100 alternating hidden-overlay updates; texture size remains 1536x768. Headset confirmation of blink removal and orientation is pending. Neither path has been benchmarked for the full keyboard. Measure CPU cost, upload cost, and visible input feedback at the target resolution before deciding on the production bridge.


Sources: [SkiaSharp](https://github.com/mono/SkiaSharp), [SkiaSharp GPU contexts](https://learn.microsoft.com/en-us/dotnet/api/skiasharp.grcontext), [OpenVR texture APIs](https://github.com/ValveSoftware/openvr/blob/master/headers/openvr.h).

## Implemented typing milestone

`KeyboardState` owns independent pointers, focused controller identity, captured keys, shared-key reference counts, and repeat timing. Both panel and handle enable MultiCursor. OverlayPointers routes events by controller identity instead of treating the cursor index as a permanent hand identity. The captured log showed slot 0 switching from device 8 to device 7 without FocusEnter, causing the old ownership check to reject valid presses. Ambiguous events without a controller are rejected rather than attributed to the last primary hand. The keyboard continues processing focus, motion, and releases during target-change cancellation. During a grab only its controller loses keyboard capture; the other controller keeps typing, repeat, and shared logical modifier state. Input requires a focused pointer, valid key bounds, matching controller identity, and a recent down newer than the last release. Mouse movement may release a captured key but cannot press another while the trigger remains held. Repeating keys start after 450 ms and repeat every 60 ms; stalled frames emit at most one repeat per key. Enter, Escape, Insert, function keys, and modifiers do not repeat.

`WindowsKeyboard` injects physical scan codes through the x64 `SendInput` ABI and checks every result. It tracks only its own downs and releases those on cancellation. Physical Shift/Ctrl/Alt/Win already held are borrowed without sending its key-up; another already-held physical key rejects a duplicate down. Pointer loss, tracking loss, dashboard hiding, foreground window/layout changes, and shutdown cancel owned keys. The foreground HWND and its thread's HKL are checked each frame and immediately before every complete stroke/repeat. A stroke is a single ordered SendInput batch: modifier downs, key down/up, reverse modifier ups. Accepted events are tracked for partial-batch cleanup. Extended scan codes retain their E0 prefix as key identity; the backend submits the low byte with KEYEVENTF_EXTENDEDKEY on both down and up. Normal typing never calls `SetForegroundWindow` or changes the Windows input language. Injection failures appear in the footer/log and failed key-ups are retried before accepting more input. Typed text is not logged.

The POC now follows the foreground thread HKL each frame, selecting standard US (04090409) or Swedish (041D041D) geometry and legends. It includes the number row, punctuation, Swedish å/ä/ö and ISO key, and right Alt. On Swedish, logical AltGr emits Ctrl plus extended right Alt in the balanced stroke. Unsupported layouts are identified and typing is disabled. Layout changes clear captured keys and modifier modes.

`--self-test` includes sequence tests for one-shot/locked/stacked modifiers, overlapping pointers without modifier leakage, failure cleanup, shared keys, coordinate conversion, key departure, stale/wrong-controller events, repeat, and cancellation. Added regressions cover two hands sharing a cursor slot, slot changes during capture, late releases from the other hand, pause/resume, fresh-motion recovery, and stale-motion rejection. The old post-release grab regressions still pass. The user confirmed two-hand typing and subsequently confirmed the inactive-hand grab fix. Explicit confirmation of typing while moving remains separate. `--input-check` explicitly creates a disposable Windows text field and exercises the real pointer model and SendInput backend. Mixed-case text, Space, Enter, Backspace, cancelling Shift, foreground preservation, and no remaining owned keys passed locally. The user confirmed actual in-headset typing into the scratch Notepad file, held Shift, Backspace/erasing, Space, and Enter all work. That feedback covered the earlier held-Shift build. The expanded Rich Edit test now passes mixed-case typing, Ctrl+A selection, Ctrl+Left word movement, Ctrl+Shift+Left selection, Ctrl+Shift+F with both modifiers active, all F1–F12 down/up pairs, and extended arrow flags. The shell check confirmed Win+R opens Run and Escape dismisses it without entering a command. The standalone Start-window automation was inconclusive, but the user subsequently confirmed hotkeys, F keys, and the Windows key in-headset. The test-only window temporarily attaches input queues to acquire focus; this is never used by VR typing. The --layout-check integration test passed Swedish → US → Swedish foreground detection, åäö/ÅÄÖ, AltGr symbols, digits, punctuation, dead-key é, and cancellation of armed/locked modifiers across layout changes. It uses already-loaded layouts on its own test thread and restores that thread layout and the previous foreground window.

## Following Windows input language

Resolve the foreground window with `GetForegroundWindow`, its thread with `GetWindowThreadProcessId`, and that thread's layout with `GetKeyboardLayout(threadId)`. `GetKeyboardLayout(0)` queries GoBoard's own thread and is insufficient for this requirement.

Refresh when the foreground target or its full layout handle changes. A modest polling interval is a reasonable first implementation because another application's input-language messages are not delivered to GoBoard. Revalidate the target and layout immediately before a new key press. Never activate a different Windows input language merely to match GoBoard's display.

Use the full HKL to detect changes. The language ID alone does not distinguish all layout variants, such as standard US and US International. Define initial support for specific layouts, and show an explicit unsupported-layout state for others rather than silently displaying misleading US legends.

Initial supported layouts are standard Swedish and US English. Separate physical geometry from character labels. Swedish keyboards require the ISO extra key; US commonly uses ANSI geometry. Letters are only part of the difference: punctuation, AltGr combinations, dead keys, and modifier legends also matter.

WindowsLegends contains fixed standard US/Swedish tables captured from MapVirtualKeyEx and ToUnicodeEx for all Shift/AltGr/Caps combinations. Runtime lookup never calls translation APIs: the non-mutating flag can still read pending accents, and a regression demonstrated the same problem on a separate thread. Clearing that buffer also disturbed actual composition. Static tables avoid both effects for the two explicitly supported layouts. Dead-key legends carry a small dead marker; named special keys do not undergo character translation. Cold and repeated label lookups with an accent pending both preserve actual é composition in the disposable integration test.

Sources: [GetKeyboardLayout](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getkeyboardlayout), [MapVirtualKeyExW](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-mapvirtualkeyexw), [ToUnicodeEx](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-tounicodeex).

## Sending input

Prefer physical scan-code input for ordinary keyboard behavior, letting the focused application's Windows layout perform character translation. Preserve extended-key flags and physical key identity through key-up. This supports shortcuts and Windows dead-key composition; emitting a displayed character as Unicode for every key would require separate shortcut behavior.

`SendInput` targets the system input stream, not a supplied window. The overlay must avoid stealing desktop focus. Check its return count and expose failures; Windows integrity-level restrictions can block input into elevated applications.

Track synthetic ownership so cancellation releases GoBoard's keys. Account for physical keyboard modifiers instead of blindly resetting global state. If the target or layout changes during a held chord, release the captured synthetic keys and cancel the chord before accepting another press. On overlay hiding, pointer loss, runtime disconnect, or normal shutdown, attempt to release all owned keys. Crash recovery cannot be guaranteed by in-process cleanup.

Source: [SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput).

## Controller interaction

Capture a key on pointer-down. The current POC cancels it as soon as the pointer leaves its bounds and also releases on pointer-up; moving to another key while held does not type that key. Maintain state per pointer; a single shared hover/pressed key cannot support simultaneous hands. Multiple pointers pressing the same physical key require ownership counting.

The tutorial demonstrates simple overlay mouse events and Unity button dispatch. Treat that as integration guidance, not the complete keyboard interaction model. Verify pointer identity and simultaneous presses against the selected OpenVR version and actual controllers before committing to the input path.

Ctrl, Alt, AltGr, and Shift cycle Idle → OneShot → Locked → Idle on successive clicks, following the supplied modifier-state mockup. Pointer release preserves the mode. Win has only Idle and OneShot: the first click arms a shortcut; the next click while armed sends a balanced standalone E0 5B Windows-key tap and clears logical modifiers after successful delivery. It has no locked mode or double-click timeout. A subsequent click starts over by arming; no separate Start tile remains. Modifier clicks do not consume other modifiers. An ordinary key captures all active modifiers and clears all one-shots together after a successful stroke. Repeats retain the captured chord; locked modes persist for later keys. Each stroke sends and releases its modifiers and key immediately, preventing one-shot leakage between overlapping pointers and avoiding globally held Windows modifiers. Hiding or a foreground target/layout change clears modes. One-shot keys have a mint border, label, ring, and underline; locked keys use mint fill, dark text, and a padlock. Hover adds an outline. Repeat should use a timed delay and cadence rather than frame count, and should stop on cancellation or visibility loss.

Rendering and hit testing must share a tested coordinate transform, including texture orientation, bounds, and mouse scaling. Reduce rendering work while idle and hidden; profile CPU/GPU impact while a VR application is running.

Sources: [Dashboard Overlay tutorial](https://dev.to/kurohuku/part-8-dashboard-overlay-1809), [Overlay Events tutorial](https://dev.to/kurohuku/part-9-overlay-events-4342), [Valve overlay overview](https://github.com/ValveSoftware/openvr/wiki/IVROverlay_Overview).

## Suggested design direction

Use a calm, high-contrast surface with large readable primary legends and smaller secondary symbols. Keep navigation keys visually grouped, make active modifiers unambiguous, and show the current language without requiring a settings panel. Avoid deciding the final appearance before checking legibility and target size in a headset.

## Delivery sequence

2. In-headset panel appearance confirmed; interactive 79/80-key rendering at 2532x1026 is implemented. The bridge now uses persistent OpenGL textures; headset blink verification is pending.

## Acceptance checks

- Swedish `å`, `ä`, `ö`, uppercase variants, AltGr symbols, and dead-key composition agree with Windows.
- US English has correct punctuation and geometry.
- Switching language with Windows shortcuts updates the keyboard without restarting GoBoard.
- Switching between applications with different input layouts updates both legends and behavior.
- Unsupported layouts are identified honestly.
- Ctrl+C, Ctrl+V, Shift+selection, arrows, Enter, Backspace, and Delete behave as expected in a controlled text target.
- One-shot modifiers affect only the next ordinary key, stacked one-shots clear together, locked modifiers persist, and the third click clears. Overlapping pointers do not leak a consumed one-shot into the second key.
- Moving a pointer away before release, closing the dashboard mid-chord, and disconnecting a controller leave no owned keys held.
- Clicking the VR keyboard preserves the intended Windows input target.
- Labels remain legible in-headset, and idle/hidden rendering cost is measured.

Automate pure state-machine and layout regression checks where useful. Keep real SteamVR/controller and foreground-focus behavior as explicit hardware integration checks; passing model tests is not evidence that those work.

Grab/typing regression checks pass for both hand directions: starting a grab cancels only its own keyboard capture; the other hand can type, consume Shift, and continue repeat; grab release preserves the other hand; queued input from the grab owner cannot type after release. Owner releases and focus loss still end a grab, and another hand cannot release or steal it.

Win arm/tap regression checks passed: first click sends no OS input, second sends exactly one down/up pair, third re-arms, ordinary shortcuts still consume Win, other logical modifiers do not contaminate the bare tap, and failed delivery preserves the arm for retry.

Inactive-hand grab acceptance: the user reproduced the interaction with grab-event tracing enabled and reported it working. Both overlays read back MultiCursor=true. The trace contains primary slot 0/device 7 and secondary slot 1/device 8 grab starts, owner releases, and unrelated other-hand focus changes that do not cancel the capture. Legacy controller-state polling is unavailable on both hands in the dashboard; the observed release path is the identified overlay pointer-up event.
